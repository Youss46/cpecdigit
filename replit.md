# M15 EduTech — Multi-Tenant Academic Management Platform

## Overview
M15 EduTech (formerly CPEC-Digital) is a multi-tenant SaaS academic management Progressive Web App (PWA) designed for educational institutions. It offers multi-role workflows for Admins (Directeur, Scolarité, Planificateur), Teachers, and Students, aiming to streamline academic operations, improve communication, and provide robust reporting and management tools. The project's vision is to enhance efficiency in educational administration and provide a modern, accessible platform for all stakeholders.

Tenants (schools) are resolved at login from the user's email — there are no subdomains. A super-admin dev portal at `/dev` (protected by `DEV_MASTER_KEY`) lets the operator create new schools (tenant + admin user + activation key in a single form) and manage activation keys, directors, and tenants.

## System Architecture

### Monorepo Structure (pnpm workspaces)
The project utilizes a monorepo structure managed by pnpm workspaces:
- `artifacts/api-server/`: Express 5 REST API backend.
- `artifacts/cpec-u/`: React + Vite frontend PWA.
- `mockup-sandbox/`: UI component development sandbox.
- `lib/db/`: Drizzle ORM + PostgreSQL schema.
- `lib/api-spec/`: OpenAPI YAML specification.
- `lib/api-zod/`: Zod schemas generated from OpenAPI.
- `lib/api-client-react/`: React Query hooks generated by Orval.

### Tech Stack
- **Frontend**: React 19, Vite 7, Tailwind CSS 4, shadcn/ui, TanStack Query, Wouter, Framer Motion, Lucide React.
- **Backend**: Express 5, TypeScript, express-session, multer (file uploads), web-push.
- **Database**: PostgreSQL, Drizzle ORM, pg driver.
- **Validation**: Zod, Drizzle-Zod.
- **Tooling**: pnpm workspaces, tsx, esbuild, Orval codegen.

### Key Features and Technical Implementations
- **Multi-role System**: Supports Admin (Directeur, Scolarité, Planificateur), Teacher, and Student roles with distinct portals and permissions.
- **Academic Management**: Manages classes, subjects, teaching units, semesters (linked to classes via LMD referential), and annual promotions. Semesters are now tied to specific classes with `classId`, `semesterNumber` (1 or 2), and `niveauLmd` (L1-M2). A unique constraint `(classId, academicYear, semesterNumber)` enforces max 2 semesters per class per year. The admin semesters page groups semesters by class, showing paired semester slots with progress and annual average calculability indicators.
- **Grade Management**: Includes teacher grade entry, approval workflows, and retake session management. Each generated grade report (bulletin) embeds a unique QR code for verification.
- **Scheduling & Attendance**: Features timetable management with conflict detection, bulk schedule generation (`Programmation par période`), and attendance tracking with justification workflows. Role-based secure filtering for schedules is implemented for admins, teachers, and students.
- **Suivi des Heures (Hour Tracking)**: Hours are counted as "realized" when a scheduled session (schedule_entries) has a matching submitted attendance sheet (attendance_sessions with sentAt != null). No admin validation step required. Status is computed dynamically based on elapsed semester time vs actual progress: A_JOUR (on track), A_SURVEILLER (slightly behind), EN_RETARD (significantly behind), NON_DEMARRE (no sheets submitted yet). The admin page shows planned/realized/remaining hours, session counts, progress bars, and dynamic status badges with CSV export.
- **Communication**: Integrated messaging with file attachments and Web Push notifications (VAPID).
- **PWA Capabilities**: Designed as a Progressive Web App with offline sync support and mobile-friendly design.
- **Jury Spécial**: Module for end-of-year special jury deliberations, traceability, bulletin updates, and PDF PV generation.
- **Digital Student ID Card (`Carte Étudiante Numérique`)**: Generates digital ID cards with QR codes, includes a public verification page, and supports admin generation/invalidation.
- **Teacher Evaluation (`Évaluation des Enseignants par les Étudiants`)**: Anonymous student evaluation module with a multi-step wizard, weighted scoring, and detailed admin/teacher reporting views. Ensures anonymity and requires a minimum evaluation threshold.
- **Parent Space (`Espace Parents`)**: Parent account system linked to student accounts, providing access to results, absences, and schedules. Automated notifications are sent to parents for absences and published semester results.
- **Payment Reminder Notifications (`Notifications de Rappel de Paiement`)**: Automated daily push notification system for fee reminders (J-7, J-3, J0, J+7) with a detailed log. Payment confirmations trigger immediate push notifications.
- **Individual Academic Tracking (`Suivi Académique Individualisé`)**: Provides admin and student views for academic performance tracking, including progression curves, subject-wise grades, absence rates, and automatic alerts for at-risk students based on multi-criteria analysis.
- **Multi-Year Comparative Dashboard (`Tableau de Bord Comparatif Multi-Années`)**: Analyzes academic performance over multiple academic years, including KPIs, success/failure rates, absence trends, and identification of high-failure subjects.
- **Grade Dispute Management (`Gestion des Réclamations`)**: Implements an official grade dispute workflow with configurable periods, student submission wizard, teacher response, and admin arbitration. Features immutable audit logs and push notifications at every stage.
- **Centralized PDF Service**: Client-side PDF generation engine (`jspdf`, `jspdf-autotable`) creating consistent documents (bulletins, attendance sheets, timetables, etc.) with institutional branding. An Admin "Centre de Documents" aggregates all available exports.
- **Online Homework & Assessment Module (`Devoirs & Évaluations en ligne`)**: Full-featured online assessment system with anti-cheat. Teachers create interactive assignments with 7 question types (QCM, QCM multiple, Vrai/Faux, texte libre, ordre, correspondance, numérique), configurable per-class targeting, and 8 individually-toggleable anti-cheat options. Anti-cheat system enforces mandatory fullscreen (requestFullscreen API), blocks copy/paste/cut/contextmenu/keyboard shortcuts (Ctrl+C/V/U/A/PrintScreen), detects tab/window changes via `visibilitychange` event (3 strikes → auto-submit with TRICHERIE_DETECTEE status), and generates server-side seeded Fisher-Yates shuffle (unique per student, stable on reload). Server-side timer validates submission time (fin_prevue stored in DB). Auto-save every 30 seconds. Automatic correction for all objective types; manual correction flagged for free-text. Teacher surveillance report shows per-student incidents, timing, and scores, with ability to cancel sessions or grant retry attempts. Students see their detailed results question-by-question with correct answers and explanations. 8 new DB tables (CREATE TABLE IF NOT EXISTS in migrate-devoirs.ts), 12 API routes at /api/devoirs, nav links in teacher and student menus. Notifications sent to students on devoir publish, and to teacher on detected cheating.
- **Digital Library (`Bibliothèque Numérique`)**: Full-featured resource sharing module. Teachers upload PDF, Word, PowerPoint, images, archives, YouTube links, and external links per subject/semester/class. Students browse by UE/subject tree, preview/download resources. Enhanced with: interactive quizzes (QCM, multi-select, true/false, free text) created by teachers and taken by students with instant scoring/feedback; automatic time-tracking per resource with a "Mon Suivi" progress dashboard; and a teacher engagement analytics tab showing consultation counts, time spent, quiz participation, and average scores.

### Running the Application
The application runs as two separate processes:
- **API Server (Express)**: Runs on port 8080.
- **Frontend (Vite)**: Runs on port 5000, mapped to external port 80. Vite proxies `/api/*` and `/srv/*` requests to the API server.

### Multi-Tenancy
Every primary table carries a `tenantId` foreign key to a central `tenants` table. A `tenantMiddleware` reads `req.session.tenantId` and exposes it on `req` so all routes can scope their queries. User emails are unique per `(email, tenantId)` rather than globally. Login finds the user by email across all tenants, then sets `session.tenantId` on success.

### `/srv/*` Path Workaround (Replit Load Balancer)
**Critical**: Replit's external load balancer returns `502 Bad Gateway` for any path starting with `/api/*`, even though those paths work fine on `localhost`. To bypass this:
1. The Express API server mounts every router on **both** `/api` and `/srv` (`app.use(["/api", "/srv"], router)`).
2. Socket.IO is served at `/srv/socket.io` (the only path; the client matches).
3. The Vite dev proxy forwards `/srv/*` straight to the API server (no rewrite — backend accepts `/srv/*` natively).
4. `artifacts/cpec-u/src/main.tsx` installs a global `window.fetch` interceptor that transparently rewrites every `/api/*` URL to `/srv/*`. This means the 367 existing `fetch` calls and React Query keys in the codebase did not need to change.
5. The service worker (`artifacts/cpec-u/public/sw.js`) also rewrites `/api/*` to `/srv/*` for direct browser fetches (e.g. `<img src="/api/uploads/...">`) that bypass `window.fetch`.

When updating the service worker, **always bump `CACHE_NAME`** (e.g. `m15-edutech-v12` → `v13`) so the browser detects the change and clears the old cache. The SW uses a network-first strategy — never cache-first — so deploys are immediately picked up.

### Dev Portal Authentication (`/dev`)
Token-based, no session cookies. The frontend computes `SHA-256("dev-token:" + password + ":m15edutech")` client-side, stores it in `localStorage["m15-dev-token"]`, and sends it as `Authorization: Bearer <token>` on every request. The backend validates by recomputing the same hash from `DEV_MASTER_KEY` and comparing.

### UI/UX Decisions
- Frontend utilizes React 19, Vite 7, Tailwind CSS 4, and shadcn/ui for a modern, responsive, and mobile-friendly design.
- Consistent institutional branding (header/footer, logo, gold accent bar) applied to all generated PDF documents.
- Interactive components like multi-step wizards for evaluations and grade disputes, and data visualization (radar charts, line charts, bar charts) for academic tracking and comparative reports.
- Color-coded scores and alerts are used for quick visual interpretation in evaluation and academic tracking modules.

## Deployment Architecture

### Frontend → Vercel
- **Config file**: `artifacts/cpec-u/vercel.json`
- **Vercel project root directory**: `artifacts/cpec-u`
- **Build command**: `cd ../.. && pnpm install --frozen-lockfile && pnpm --filter @workspace/cpec-u run build`
- **Output directory**: `dist/public`
- **API proxy**: Vercel rewrites `/api/*` → `https://$BACKEND_HOST/api/*` so the browser never makes cross-origin requests — no CORS headaches, session cookies work as same-origin.
- **Required Vercel env var**: `BACKEND_HOST` — set to the Railway hostname (e.g. `my-app.railway.app`, no `https://`).
- **SPA routing**: All non-asset routes fall through to `index.html`.

### Backend → Railway
- **Config file**: `railway.toml` (project root)
- **Build command**: `pnpm install --frozen-lockfile && pnpm --filter @workspace/api-server run build`
- **Start command**: `pnpm --filter @workspace/api-server run start`
- **Health check**: `GET /api/healthz`
- **Required Railway env vars**: `DATABASE_URL`, `SESSION_SECRET`, `DEV_MASTER_KEY`, `PORT` (auto-set by Railway), optionally `CORS_ORIGINS` (comma-separated allowed origins).

### Fetch Interceptor (Replit-only)
The `window.fetch` interceptor in `main.tsx` that rewrites `/api/*` → `/srv/*` is **gated to the Replit hosted environment** (`*.replit.dev`, `*.repl.co` hostnames). It does not run on Vercel or localhost.

### Monolithic / Self-Hosted Mode
Both packages can still be built together and the backend will serve the frontend static files from `artifacts/cpec-u/dist/public` if that directory exists at runtime.
